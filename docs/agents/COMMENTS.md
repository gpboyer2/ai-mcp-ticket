# 注释规范

> 本文件是「注释怎么写」的唯一权威清单（行数 + 内容），由根目录 [`AGENTS.md`](../../AGENTS.md) 引用。
> 检查脚本 `scripts/check-comment-limit.mjs` 按本文件的口径实现，提交时由 `.githooks/pre-commit` 强制执行。

## 一、管哪三件事

1. **别太长**：注释一多，代码被挤到看不见，改的时候还得同步维护这些解释。
2. **只写客观作用**：说清这段代码、这个函数是干什么的，不写来龙去脉。
3. **不用黑话**：同一个东西全项目只用规范叫法，不许另起外号。

## 二、硬上限

按注释块的有效行数算，`@标签` 行和空行**不计数**：

| 注释块类型 | 上限 | 判定方式 |
| --- | --- | --- |
| 文件头注释 | ≤ 5 行 | 位于文件最前面（前面只有空行和 shebang），通常带 `@file` |
| 函数注释 | ≤ 2 行 | 紧贴着 `function` / `class` / 方法定义 / 箭头函数常量 |
| 普通注释 | ≤ 1 行 | 其余所有块注释与连续 `//` 行 |

`@param` `@returns` `@file` 这类标签行按原样保留，不占额度，也不许改写它们的格式。

## 二之二、只写客观作用，不写「为什么」

注释的职责是**说清这东西是什么**，不是解释当初为什么要加它。

| 不要写 | 要写 |
| --- | --- |
| `为什么需要防抖：网络抖动会连续触发，实测卡死过三次` | `防抖：同一事件 300 毫秒内只触发一次` |
| `为什么不用数组 push：常驻进程会无限增长，压垮内存` | `定长环形缓冲：写满后覆盖最旧的一条` |
| `之所以放这里而不是 CLI：变体是研究口径` | `变体参数组装，供矩阵回测与 CLI 共用` |

判断标准一句话：**这句话是在描述代码，还是在讲历史？** 讲历史的一律删掉，那是 `docs/` 和 git 提交信息该管的事。

`为什么` `原因在于` `之所以` `原因是` 这几个词出现在注释里就会被拦。

## 二之三、不用黑话

| 黑话 | 规范叫法 |
| --- | --- |
| 腿 | 信号规则 |

全项目一个东西只许一个名字。发现新外号，先把它加进 `scripts/check-comment-limit.mjs` 的 `JARGON` 表，再全项目 grep 改掉。

## 三、举例

文件头超限：

```js
/**
 * @file
 * 事件循环延迟监控：判定「沉默是不是我们自己卡住造成的」。
 *
 * 用 Node 内置的 `perf_hooks.monitorEventLoopDelay`，不自己拿 setInterval 时间戳相减去猜。
 * 它是官方专门做这件事的 API：内部按 resolution 采样，记录「定时器本该触发」与
 * 「实际触发」的差值，`max` 就是这段时间内最长的一次卡顿。
 *
 * 为什么必须有它：后端同步 SQLite 全表扫会卡住事件循环数秒，这期间收不到任何 WS 消息。
 * 只看「多久没收到消息」的看门狗会把这判成「对端死了」，然后掐掉一条健康连接——
 * 这是「前后端都起着却看不到数据」的直接推手之一。
 */
```

改成 3 行正文就合规：

```js

 * @file
 * 事件循环延迟监控：判定「沉默是不是我们自己卡住造成的」。
 *
 * 用 Node 内置的 `perf_hooks.monitorEventLoopDelay`，不自己拿 setInterval 时间戳相减去猜。
 * 后端同步 SQLite 全表扫会卡住事件循环数秒，这期间收不到任何 WS 消息。
```

普通注释超限：

```js

 * 本地事件循环卡顿判定：看门狗 tick 期望间隔与实测间隔的差值超过这个值，
 * 就判定「沉默是本地卡住造成的」，不许掐连接。
 * 取 3 秒：同步 SQLite 全表扫实测能卡 1~4 秒，取 3 秒能覆盖多数误判又不至于放过真死连接。
 */
loopLagThresholdMs: Number(process.env.WS_LOOP_LAG_THRESHOLD_MS || 3_000),
```

压到 1 行：


## 四、怎么执行

| 场景 | 命令 | 行为 |
| --- | --- | --- |
| 每次 `git commit` | `.githooks/pre-commit` 自动跑 | 只审这次提交新增或改写过的注释块；存量不追究 |
| 想主动体检全仓库 | `pnpm check:comments:all` | 扫全部源码，存量违规一并列出 |
| 提交前自查 | `pnpm check` | 目录布局 + 单文件行数 + 注释行数，三样一起过 |

首次 clone 后执行一次 `pnpm hooks:install`（等价于 `git config core.hooksPath .githooks`），钩子才生效。

`git commit --no-verify` 能绕过，但这是本仓库明确不推荐的用法：绕过一次，后面就没人守了。

## 五、被卡住了怎么改

1. 先删「怎么做的过程」——那是 git 历史的事。
2. 再删「为什么这么做」——那是提交信息和 `docs/` 的事。
3. 再删「显而易见的解释」——代码本身说得清的，注释不必重复。
4. 剩下的那句必须是**客观陈述**：这个函数、这个常量、这段逻辑是什么。一句话写完。
5. 真要展开，写到 `docs/` 里，代码里留一行指向文档。
