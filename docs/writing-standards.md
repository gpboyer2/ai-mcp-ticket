# 文档 / 文案 / 注释规范

本文档沉淀 ai-mcp-ticket 对「文档编写、文案、注释」的统一要求。目的：让文档、注释、文案能随仓库一起演进，不因为写死的数字或过时的兼容描述而误导人。

---

## 1. 禁止写死会变的数字

任何会随仓库演进而变化的计数、版本号、端口号、文件数，都不许写死在文档 / 注释 / 文案里。

反例：

> `npm test # 103 项自动化测试（…）`

测试项数一直在变，今天 103、明天 105，写死的那一刻它就过时了，还会骗人。

正例：

> `npm test # 自动化测试（node --test，无需外部依赖，随机端口，不碰任何固定端口）`

描述能力、约束、性质，而不是一个会漂移的快照数字。

举一反三：
- 不要写「共 N 个工具 / 共 N 张表 / 第 N 版」这类会随提交变化的数。
- 版本号、依赖数、接口数同理，能写「用 ESM、无构建步骤」就别写「Node 22.x 的某小版本具体行为」这种会过时的精确描述。
- 端口 `47321` 这种「真实实例固定端口」是约定（见 [debug-log.md](./debug-log.md)），不是会变的统计量，可写；但自测端口必须随机，别写死某个具体自测端口。

---

## 2. 禁止兼容性 / 升级概念、禁止旧逻辑兼容分支、禁止「新增 / 注意」文案

写代码和文档要当作「一次生成、一体成型」：它就是现在的样子，没有「从前」和「以后」。

禁止的写法：
- 兼容性描述：「为兼容旧版…」「为了保持向后兼容…」「旧接口仍可用…」
- 升级描述：「已升级到 X」「从 Y 迁移到 Z」
- 兼容分支：在代码里留「如果是老数据结构就走这条」「兼容旧逻辑」的 if 分支。
- 渐进式标注文案：「这里是新增的…」「注意：本节为新增」「新功能如下」。

正确心态：文档描述的是当前事实，不交代来龙去脉，也不标记哪些是「后来加的」。读者只关心此刻它是什么，不关心它怎么变来的。

---

## 3. 举一反三、以此类推

看到一处写死的或可兼容化的写法，就顺手把同类都改掉：
- 同一份文档里还有别的写死数字？一起改。
- 注释里有「新增 / 注意 / 兼容」？一起删。
- 代码里有兼容旧逻辑的分支？一并清理（遵循 AGENTS.md 第五节「改代码」的「更少路径」原则，一个规则只一份实现）。

不要只改被点名那一处，要让同类问题在同一轮里清零。
